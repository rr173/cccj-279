# 检修事实拆分系统

把带稳定 ID 与递增修订号的事件流，物化为**按工单 × 实际位置拆分的检修事实**，
并单列**未归属 / 待核**备查账。所有时间区间均为半开 `[lo, hi)`。

## 目录

- `maint_facts/intervals.py` — 半开区间、相交、真实时间并集
- `maint_facts/events.py` — 事件模型与修订协议（同号重送 / 异内容拒绝 / 高修订替换）
- `maint_facts/engine.py` — 事实引擎：扫描线归属、增量修订、提案/发布、备查账
- `maint_facts/availability.py` — 产线可用性账：分段状态、时长与复算依据（只读查询）
- `demo_handcalc.py` — 7 个手算例（含逐条断言与净变化展示）
- `demo_availability.py` — 可用性手算例（三态裁定/共享依赖/合并/环/只读/访问边界）
- `property_test.py` — 400 轮随机修订，增量结果始终等价于朴素全量重算
- `availability_property_test.py` — 300 轮随机用例，边界扫描等价于逐时刻朴素裁定
- `scale_test.py` — 增量隔离与规模测试（访问量不随全局历史增长）

## 事件类型

| type | payload | 说明 |
|------|---------|------|
| `loc` | asset, loc, interval | 资产位置区间 |
| `wo` | asset, wo, interval, priority(整数) | 工单区间与优先级 |
| `down` | asset, interval | 停机区间 |
| `spare` | asset, time, qty, wo?(可选) | 备件领用时刻与数量 |

## 归属规则

1. **位置**：同一时刻命中多个不同位置值 → 待核；无位置区间覆盖 → `未知位置`
   （未知不是待核）。迁移瞬间（半开边界 `t`）归新位置。
2. **停机**：同资产重叠停机先做**真实时间并集**，每个停机时刻只计一次；
   并集后的每个时刻归当时有效工单中**优先级最高**者；最高并列 → 待核；
   无工单 → 未归属。
3. **备件**：
   - 指定工单 ID：校验同资产且当时有效，否则待核（`备件指定工单校验失败`）；
   - 未指定：按同一优先级规则唯一认领，最高并列 → 整笔待核、**不拆量**。
4. **工时**：工单按自身区间切位置累计，不看优先级、**不由停机反推**。
   工时、停机、备件三类量纲独立，绝不互相折算或重复计量。

输出 `Agg(labor, down, spare_qty)` 挂在 `FactKey(asset, wo, loc)` 上；
未归属/待核进 `ledger`，带原因码、区间与明细。

## 修订协议（同一稳定事件 ID）

- `revision` 必须正整数且严格递增；
- 同号 + 内容哈希相同 → `NOOP`（无操作，不产生新版本）；
- 同号 + 内容不同 → 抛 `RevisionConflict`（拒绝，需用新修订号）；
- 低修订号 → 抛 `RevisionRejected`；
- 高修订 → `ACCEPT`，**整份替换**旧内容（允许类型/资产变化）。

## 两阶段发布与增量

- `submit(event)` 只暂存 `Proposal`（含事实净变化、备查账撤回/新增、访问事件集、
  受影响资产窗），不改变已发布版本；
- `publish()` 提交出版本号 +1；`publish(fail=True)` 模拟发布失败，回滚提案，
  **已发布版本维持旧版**；`rollback()` 显式放弃提案。
- 增量边界：修订只重算**受影响资产**（旧版本资产与新版本资产的并集）。
  引擎按资产维护有序索引，重算窗取该资产修订后全部事件的包络，
  只访问该资产的相交索引项与领用，**其他资产完全不读取、不变更**；
  成本随受影响资产数据量线性，与全局历史总量无关（见 `scale_test.py`）。
- 备查账条目以**内容确定性 ID** 键控存储，受影响资产整体重算后键控替换，
  天然幂等，无残段重复计量。

## 产线可用性账（availability）

在已发布事实上做**只读**的分段可用性查询（不改动检修账）。
输入为同一次发布后的一批快照：现行停机事件（不论记到哪张工单）、
设备监测覆盖区间 `MonitorRecord`、带生效区间的服务依赖 `Dependency`、
各服务最少可用下级数（未配置视为 0）。

裁定规则（某时刻 t）：

1. **设备**：有现行停机事件覆盖 → 不可用（停机优先，该时段监测不计入命中）；
   否则有监测覆盖 → 可用；无覆盖 → 未知。
2. **服务**：只按当时有效且从被查服务可达的依赖裁定；相同下级同一时刻只计一个。
   已确定可用下级数 ≥ 门槛 → 可用；可用数 + 未知下级数 < 门槛 → 不可用；其余 → 未知。
3. 可达且生效的依赖中存在服务环 → 整次查询抛 `DependencyCycleError`，
   指出一条环及查询窗内其确实可达且生效的一段时间。

`AvailabilityIndex.query(service, window)` 返回覆盖整窗的分段：
每段带状态与复算依据（当时可达依赖、各服务门槛与计票、各设备状态及
命中的监测记录 ID / 停机事件 ID+修订号）；状态与依据都相同的相邻段合并，
共享依赖只记一次。`recompute_from_basis` 可仅凭依据独立复算状态。
查询按边界点扫描、按窗二分检索，只访问窗内实际可达的设备/服务/记录
（`report.accessed` 可审计），不遍历全厂历史，也不逐时间单位推进。

## 运行

```bash
python3 demo_handcalc.py   # 手算例（优先级变动/迁移点/重复停机/未归属/并列/位置歧义/修订协议）
python3 property_test.py   # 随机化等价性 + 工时守恒
python3 scale_test.py      # 增量隔离与规模
python3 demo_availability.py          # 可用性手算例（三态/共享依赖/合并/环/只读/访问边界）
python3 availability_property_test.py # 可用性随机化等价性 + 访问边界
```
